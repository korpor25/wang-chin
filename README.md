# วังชิ้นฟาร์ม — ระบบสนับสนุนการผสมเทียมโคขุน

เว็บแอปสำหรับสหกรณ์วังชิ้น บันทึกงานภาคสนามได้แม้ไม่มีสัญญาณ
แล้วส่งขึ้นระบบให้เองเมื่อกลับเข้าพื้นที่ที่มีเน็ต

## Stack

Vite + React 19 + TypeScript · react-router · Dexie (IndexedDB) · Zustand
`vite-plugin-pwa` (Workbox) — ติดตั้งลงโฮมสกรีนแล้วใช้แบบออฟไลน์ได้

## คำสั่ง

```bash
pnpm dev         # dev server (service worker เปิดใช้งานด้วย)
pnpm build       # tsc -b && vite build
pnpm preview     # เสิร์ฟ dist/ พร้อมเปิด LAN
pnpm typecheck   # tsc --noEmit
pnpm lint        # oxlint
```

## หลักการที่ยึด

**ออฟไลน์ก่อนเสมอ** — ทุกการบันทึกลงเครื่องทันทีแล้วเข้าคิว ผู้ใช้ไม่เคยต้องรอเน็ต
งานภาคสนามเกิดในคอกที่สัญญาณไม่ถึง การออกแบบจึงเริ่มจากตรงนั้น ไม่ใช่จาก API

**ระบบคิดกำหนดการเอง** — บันทึกหนึ่งครั้งไม่ได้แค่เก็บลงตาราง แต่เปลี่ยนสถานะโค
ตัดสต๊อก และสร้างงานของรอบถัดไปให้อัตโนมัติ (`data/effects.ts`)
คนไม่ต้องจำเองว่าคลอดแล้วอีกกี่วันต้องตรวจมดลูก

**ค่าชีววิทยาปรับได้ ไม่ hard-code** — ทุกตัวเลขที่ใช้คำนวณอยู่ใน `BioParams`
ปรับผ่านหน้าตั้งค่า (ง-02) เพราะที่ประชุมต้องปรับแล้วเทียบผลก่อน/หลังได้

## โครงสร้าง

```
src/
├── domain/                # ตรรกะธุรกิจล้วน ไม่แตะ UI หรือฐานข้อมูล
│   ├── types.ts           # Role, Animal, ActivityRecord, Task, BioParams, ...
│   ├── rules.ts           # กฎกำหนดการ (ค-01), golden period, THI, breeding blockers
│   └── activities.ts      # แคตตาล็อกกิจกรรม 26 รายการ ตามเอกสารแนบ ค
├── data/                  # ชั้นข้อมูล — IndexedDB ล้วน ไม่แตะเครือข่าย
│   ├── db.ts              # Dexie schema + ตัวนับ + audit
│   ├── queries.ts         # คิวรีที่หน้าจอใช้ร่วมกัน
│   ├── effects.ts         # ผลข้างเคียงของการบันทึก → สร้างงานรอบถัดไป
│   ├── sync.ts            # outbox queue, retry/backoff, conflict, retention
│   └── seed.ts            # ข้อมูลตัวอย่างสำหรับ dev
├── routes/                # หนึ่งไฟล์ต่อหนึ่งหน้า
├── components/            # AppShell, ActivityForm, ui.tsx (ชิ้นส่วนพื้นฐาน)
├── state/session.ts       # บัญชีที่กำลังใช้งาน
└── lib/                   # format (ตัวเลข/เวลาไทย), storage (โควตา/persist), image (บีบอัดรูป)
```

**ฟอร์มทั้ง 26 ตัวมาจากไฟล์เดียว** — `activities.ts` เก็บกิจกรรมเป็น data
(ใครทำ เมื่อไหร่ กรอกอะไร ระบบเอาไปคำนวณอะไรต่อ) แล้ว `ActivityForm` เรนเดอร์ตามสเปกนั้น
เพิ่มกิจกรรมใหม่ = เพิ่ม entry ไม่ต้องเขียนหน้าจอใหม่

## สิ่งที่ยังไม่จริง

ทั้งสามข้อนี้เป็น UI ที่ทำงานครบแล้วแต่ยังไม่ได้ต่อของจริง

| ส่วน | สถานะ |
|---|---|
| **Backend** | `sync.ts` → `pushOne()` เป็นตัวจำลอง สุ่ม 8% error / 3% conflict ไว้ทดสอบ UX ทุกเส้นทาง — เมื่อมี API จริงให้แทนที่เฉพาะฟังก์ชันนี้ |
| **Auth** | `state/session.ts` hard-code 4 บัญชีไว้ใน array และ `Require` ใน `App.tsx` กันได้แค่ชั้น UI — ต่อ backend เมื่อไหร่ **ต้องตรวจสิทธิ์ซ้ำฝั่งเซิร์ฟเวอร์เสมอ** |
| **Persistent storage** | `lib/storage.ts` มี `requestPersist()` แต่ยังไม่มีหน้าไหนเรียก ข้อมูลจึงยังอยู่ในสถานะ best-effort ที่ระบบลบทิ้งได้เมื่อพื้นที่ใกล้เต็ม |

## ข้อจำกัดของ PWA ที่ออกแบบเผื่อไว้แล้ว

วัดจริงบน Android (Chrome, RAM 4 GB, ติดตั้งเป็นแอปแล้ว) ก่อนเริ่มเขียนระบบนี้ ได้โควตา 14.5 GB
และ `persisted: true` — พื้นที่ไม่ใช่ข้อจำกัด แต่มีสองเรื่องที่มีผลกับโค้ดโดยตรง

- **นับ `syncStatus` ด้วย `count()` ไม่ได้** — โตแบบ O(n) (500,000 แถว = 5.1 วินาที)
  เพราะทุกแถวมีค่า index เดียวกัน index จึงช่วยอะไรไม่ได้
  → ตาราง `counters` เก็บยอดไว้ตรง ๆ แล้วบวกลบตอนเข้า-ออกคิวแทน
- **เหตุผลที่ลบข้อมูลเก่าไม่ใช่พื้นที่ไม่พอ** (โควตา 13 GB เทียบกับ 5 MB/ปี)
  แต่เพราะยิ่งค้างในเครื่องนานยิ่งเสี่ยงหายไปพร้อมเครื่อง และเสี่ยงข้อมูลรั่วถ้าเครื่องหาย
  → `pruneOldData()` ลบเฉพาะที่ซิงค์แล้วและเก่ากว่านโยบาย

ต้องเสิร์ฟผ่าน **HTTPS หรือ localhost** เท่านั้น — Service Worker และการติดตั้ง PWA
ไม่ทำงานบน `http://` ที่เป็น IP ในวง LAN
